# aeboard architecture

aeboard is one Go binary serving a single-page app. The SPA embeds the BlockSuite edgeless editor; the binary is the Yjs sync server for it and the only writer of the board repository. This document records how the pieces fit and why they were chosen.

## Components

```
browser ── BlockSuite editor ── Y.Doc ── y-websocket ──┐
                                                       │  /api/v1/sync/<board>
aeboard ── ygo websocket server (rooms = boards) ──────┘
              │ LoadDoc / StoreUpdate (ygo coalesces: 2s window, 10s cap)
              ▼
           boards.Store (in memory) ── write-behind ──► Backend
                                                         ├─ DirBackend: files under --data
                                                         └─ gitbackend: commits ⇄ remote (push / fetch / merge)
           blobs.Store (attachments, content-addressed, not in git)
```

## Compatibility spike: BlockSuite over ygo

The first step was a spike to prove that BlockSuite's edgeless editor works over a plain Yjs server written in Go. Outcome: **it fits**, with four findings that shape the code.

1. **One board is one Y.Doc is one ygo room.** BlockSuite's reference workspace keeps every document as a Yjs *subdocument* of a root doc, and y-websocket does not carry subdocument contents. aeboard does not need a multi-page workspace, so `web/src/board/workspace.ts` implements BlockSuite's public `Workspace`/`Doc` interfaces with the board as a standalone Y.Doc (guid = board id). That doc is the only thing synced. The root doc only exists because the interfaces expose it, and it stays local.
2. **Presence works through y-protocols awareness**, which ygo relays: cursors with names and selection frames render through BlockSuite's own remote-selection widget. Two details matter. The editor must be loaded with `store.load()`, not `doc.load()`, so the selection extension subscribes to remote awareness. Every awareness state must also carry `selectionV2`, because BlockSuite reads it from peers without a null check.
3. **New boards start from a fixed seed** (`internal/seed/seed.bin`, generated by BlockSuite itself via `web/scripts/gen-seed.ts`). Two browsers opening a brand-new empty board at once used to create two root blocks. The seed is written by clientID 0 with fixed ids, so every replica starts from identical Yjs items, and the server hands it out for any board without state.
4. **A restart neither loses nor duplicates anything.** After a restart, a reconnecting client re-sends its state. The server's copy already holds those items, so the merge is a no-op. Edits made while the server was down reach the other browsers once it is back.

BlockSuite also needs a few host-side settings, all in `web/src/board/editor.ts`:
- a `DocModeProvider` that says "edgeless"; without it the element toolbar never shows;
- the AFFiNE theme stylesheet;
- the template panel's contents, vendored from AFFiNE's MIT frontend (`web/vendor/affine-templates`);
- `@preact/signals-core` pinned to 1.13, because 1.14 changed batching in a way that leaves BlockSuite's toolbars stale.

The last published npm release of `@blocksuite/affine` is 0.22.4 (July 2025). Only the MIT packages are used, never `@blocksuite/blocks`/`presets` (MPL-2.0) or AFFiNE's EE-licensed backend.

ygo is pinned (`v1.55.0`) and touched in one place (`internal/server`): the websocket server, its persistence interface, `Authorize`, `GetDoc`/`BroadcastUpdate` for injecting fetched changes, `OnUnloadDocument`. The CRDT functions are used for merging states. If the project stalls, this surface is small enough to replace.

## Storage

Each board is a directory, identical in the plain-file and the git backend:

```
boards/<id>/board.json   title, tags, created/updated
boards/<id>/state.jsonl  the Yjs state as text — the source of truth
boards/<id>/doc.json     the "blocks" map as sorted, indented JSON — for people and diffs, never read back
```

**Why the state is a Yjs log, not just JSON.** Yjs tells edits apart by their item ids (client, clock) and the neighbours each item was inserted between; that is what lets a reconnecting browser re-send its state, or two replicas merge, without duplicating anything. A board rebuilt from plain JSON would get fresh ids every time. So the source of truth keeps the ids — but as text, not binary: `internal/ytext` writes the Yjs V1 update as JSON lines, one per item (`{"id":[client,clock],"left":…,"parent":…,"key":…,"string":"…"}`) and one per client of deleted ranges, and reads it back to the identical bytes (values keep their wire type, objects their key order). Every write checks that round trip before anything is stored. The text is about three times the binary size; git compresses it, and the diffs show which items a commit added or deleted. Boards stored before this as `state.bin` are still read and converted by their next write.

**Write-behind.** ygo already folds a burst of updates into one `StoreUpdate`. On top of that, `boards.Store` answers from memory and only marks a board dirty. Its flusher writes a board once nobody has changed it for 5s, at the latest 60s after its oldest unwritten change, when the last participant leaves the room, and on shutdown. Each write is one commit per board, authored by the people who were in the room. An edit that lands while its board is being written keeps the board dirty for the next write. An update the state already contains, such as a reconnecting peer re-sending, is not a change.

**Attachments** (images, stickers, files) are not part of the Yjs state; the doc only holds their key. They go to `blobs.Store` under `--data/blobs`: content-addressed by SHA-256 (BlockSuite's own key), with the hash checked on upload, one copy per content, never deleted by a client. The HTTP route is per board (`/api/v1/boards/<id>/blobs/<key>`), so access follows the board's rights. Today the store is local to one server. A shared store (S3-compatible, or a separate git LFS-style repository) is the open item for running several servers.

## Git sync

`internal/gitstore` is the generic half of aeman's `pkg/gitstore`. Commits are built through go-git plumbing without a worktree. The clone is shallow, and fetch drives upload-pack by hand, offering only the known remote tip. Push reports a reliable "rejected".

`internal/gitbackend` runs a loop: push after every write, fetch every `--fetch-interval`.

- **Fast-forward** when there are no local commits on top.
- **Merge commit** otherwise. For every board that differs between the two tips, the two Yjs states are merged (a CRDT: every edit from both sides survives) and the metadata of the side updated last is kept. A rejected push is just fetch, merge, push again. There are no conflicts to resolve by hand.
- **Fetched boards reach open rooms at once.** The store merges them and returns, per board, the update its live room is missing. The server applies it to the ygo doc and broadcasts it.

The header badge shows the number of boards with uncommitted changes plus the number of unpushed commits, the same pill aeman shows. A warning appears when pushes stall for 5 minutes or fail; the state comes over `/api/v1/status/events` (SSE).

## Identity and rights

- **Local mode** (`aeboard serve`) acts as the account the `gh` CLI is logged in as, like `aeman serve`. That login is on the cursor and authors the commits, and `gh`'s token pushes to an https remote.
- **Hosted mode** turns on when a GitHub client id and secret are set. It is aeman's sign-in, ported (`internal/server/auth.go`, `sessioncrypt.go`, `access.go`, `internal/forge`) without aeman's MCP authorization server:
  - `/auth/login` sends the visitor to GitHub with a random state bound to the browser by an HttpOnly, SameSite=Lax cookie (Secure behind https); `/auth/callback` refuses a state that is not this browser's, trades the code for the visitor's token and opens a 14-day session; `POST /auth/logout` ends it. A GitHub App's user token expires after 8 hours and is renewed ahead of time with its single-use refresh token, one renewal per session at a time.
  - Sessions are kept in memory and, with `AEBOARD_SESSION_KEY`, in a file sealed with AES-256-GCM. Without the key nothing is written; with a wrong key the file is ignored and everyone signs in again.
  - Rights come from the visitor's permission on the board repository, asked as the visitor (`GET /repos/{owner}/{repo}`) and cached per login for a minute; a stale answer is served while it is re-asked in the background, and stands while GitHub is unreachable. A token GitHub refuses is renewed once, then the session is dropped (401). One gate in front of `/api/v1` applies the answer: no session is 401, no access is 403, read access refuses every write with 403 and gets a read-only sync socket (ygo's `ConnectionConfig.ReadOnly`, which drops the peer's updates and awareness). Writes must also come from the public origin. `/api/v1/me` reports the identity and the access, so the SPA shows the sign-in, a "no access" page, or a view-only board.
  - The session is the request's identity: the login on the cursor, the room's editors and the commit author. Read-only visitors are never named as editors.
  - The server's own git pushes use the same GitHub App's installation token, minted per request and renewed five minutes before it expires; `AEBOARD_GIT_TOKEN` and `gh` remain the fallbacks.
  - Rights are checked when a socket opens. A visitor demoted while connected keeps their socket until it reconnects.
  - The `forge.Forge` interface keeps GitLab possible; only GitHub is implemented.
